# 评测

评测回答三个问题：**在什么条件下**、**得到了什么结果**、**失败在哪里**。没有这三样，任何"能力提升"都只是叙述。本文定义 `agi-lab` 的评测哲学、指标口径、套件分工、结果归档与反自欺规则。评测台的架构位置（`eval` 层、`Tracer`、回放）见 [02-architecture](02-architecture.md) 的"可观测与评测"，本文不重复。

## 1. 评测哲学

### 1.1 独立 grader，不采信 agent 自评

Agent 对自己的输出有两类天然偏差：它既是被评者，又参与"什么算完成"的叙述；真实模型还倾向声称任务已完成。因此：

- **成功只由外部 grader 判定。** 契约层已固化这一点：`RunResult.success` 的文档明确"只由外部 grader 判定，不采信 agent 自评"（见 `agi_lab/types.py`）；任务通过 `TaskSpec.grader_id` 指定评分器。
- **grader 与被评系统分离。** grader 只读取允许的证据（最终答案、工作区产物、必要的运行记录），不读取 agent 的自我评价，不导入认知/记忆模块的逻辑；grader 由实现 agent 之外的人评审。
- **grader 自身要被测试。** 对"把答案写进文件让 grader 读到""用错误格式伪造完成"这类作弊路径，必须有专门的对抗用例。grader 被欺骗是评测事故，不是 agent 的胜利。
- **critic 的结论不是成功判定。** 运行时的 critic 只用于驱动循环（决定该步是否通过、是否重规划），不能替代外部 grader；两者混淆会把"自己觉得完成"变成"评测通过"。

### 1.2 held-out

能力套件的任务在结果产生前冻结，并且**从未**用于提示词示例、调试、人工挑选或阈值调整。规则：

- 任务分为 dev 与 eval 两个划分；任何被用于调试提示词或修 bug 的任务自动降级为 dev，不得再计入能力结论。
- eval 任务集的哈希在首跑前归档；首跑之后不得增删条目或修改 grader 严格度。
- 消融实验的"训练教训"只能来自同任务族的 train 划分，eval 划分的信息不得进入记忆。

### 1.3 消融实验

任何机制收益都必须以"只改一个变量"的配对对比呈现：

- 两臂的任务、种子、模型、预算、温度、提示词模板完全一致；唯一差异是被检验的机制（如注入/不注入教训）。
- 先写协议（假设、主指标、样本量、分析计划），再跑实验；不允许看到结果后更换主指标或挑选任务族。
- 同时报告收益与代价：记忆注入增加 token；更高成功率可能伴随更高成本。只报收益不报成本的结论不成立。

### 1.4 重复采样与方差

真实模型是随机系统，同一任务重复运行结果不同；方差本身是结论的一部分。

- 能力套件每任务至少重复 3 次；消融实验每臂至少 20 个配对样本。
- 报告分布而不是最好成绩：至少给出均值、中位数、最小值、最大值（或区间）；禁止只报 `max`。
- 区分两类方差：任务间（任务难度不同）与任务内（采样随机）。重复次数不足时只能作方向性结论。
- 小样本（< 20 个 run）的百分比只用于观察趋势，不能用于宣称显著差异；区间估计用 bootstrap 或 Wilson 区间，不用正态近似。

### 1.5 评测先于能力

这是项目的硬约束（见 [06-design-decisions](06-design-decisions.md) ADR-009）：先有独立 grader 与可复跑的任务集，才允许出现能力数字。顺序不能倒置——否则任务集会不自觉地围绕已有实现设计，评测沦为背书。

## 2. 机制套件与能力套件

两类套件回答不同问题，**不得混用结论**：

| 维度 | 机制套件 | 能力套件 |
|---|---|---|
| 回答的问题 | 运行时机制是否正确？ | 在真实模型下能做到什么程度？ |
| provider | 脚本化离线 `MockLLM` | 真实 provider（OpenAI 兼容，如 DeepSeek） |
| 是否需要 API key / 网络 | 不需要 | 需要 |
| 确定性 | 确定性：同脚本 + 同 seed 结果一致 | 随机：报告分布与方差 |
| 判定方式 | 断言通过/失败（二元） | 指标报告（成功率为首要指标），不追求"整体 pass" |
| 覆盖内容 | 预算终止、路径围栏、审批拒绝、JSON 修复、重规划接线、记忆持久化往返、trace schema、确定性 | 计划质量、工具选择、纠错、跨任务复用、成本 |
| 执行时机 | 每次改动后（CI 级回归） | 里程碑节点与发布前；按预算控制重复次数 |
| 失败处理 | 失败即阻塞合并 | 失败样本必须保留并公开，结论按 04 的规则解读 |
| 禁止用途 | **禁止**把通过率当作能力证据 | 禁止用于调整 eval 划分或挑选指标 |

规则：

1. 机制套件的价值在于"运行时不允许坏"，它证明的是工程正确性，不是智能水平。mock 通过不代表能完成真实任务——把 mock 成绩写成能力结论属于反自欺检查单中的明确违规。
2. 能力套件在缺少 API key 时必须**显式 SKIPPED**（非零退出码 + 报告标注），不得记为 pass、不得静默跳过。
3. 一个改动如果同时修改运行时与评测口径，必须拆分或分别归档；否则无法判断收益来自机制还是测量。

## 3. 指标定义与公式

记号：`R` 为某套件的 run 集合，`T` 为任务集合，`n_t` 为任务 `t` 的重复次数，`success(r) ∈ {0,1}` 为外部 grader 判定，`s(r)` 为 `Metrics.steps`，`tok(r)` 为 `Metrics.total_tokens`。所有指标从 `runs/<run_id>/trace.jsonl` 与结果记录自动计算，禁止手工填报。

| 指标 | 定义 | 公式 | 数据来源 | 报告要求 |
|---|---|---|---|---|
| 任务成功率 | 通过任务的占比 | 单任务 `p̂_t = (1/n_t) Σ success(r_ti)`；宏平均 `SR_macro = (1/|T|) Σ p̂_t`；微平均 `SR_micro = Σ success / Σ n_t` | grader 判定 + run 记录 | 报告宏平均为主、微平均为辅；给出每任务 min–max 与 n；小样本附区间 |
| 平均步数 | 每个 run 实际执行的计划步数 | `s̄ = (1/|R|) Σ s(r)`；同时报告 `s̄_success`（仅成功的 run）与 `s̄_fail`（仅失败的 run） | `Metrics.steps`、`Plan` | 必须分开报成功/失败，避免幸存者偏差；附中位数 |
| token 成本 | 每个 run 的 token 消耗与总花费 | `t̄ok = (1/|R|) Σ tok(r)`；`cost = Σ prompt_tokens×p_in + Σ completion_tokens×p_out`；`cost_per_success = cost / Σ success` | `Metrics.prompt_tokens/completion_tokens`、价格表 | 分别报输入/输出 token；报告"每解决一个任务的成本"；跨价格表不能直接比 |
| 自我纠正率 | 出现过失败步、但最终成功的 run 占比 | `SCR = |{r ∈ R : failed_step(r) ∧ success(r)}| / |{r : failed_step(r)}|` | trace 中 critic/格式失败事件、`PlanStep.attempts`、`Metrics.tool_failures`、`Metrics.format_repairs` | 分母为 0 记 `N/A`（不是 0%）；必须同时报告分母；"失败步"定义为某次计划步骤 attempt 未通过 critic 或未以 FINAL 完成 |
| 重规划有效率 | 重规划之后是否换来推进 | 事件级 `RER = |{replan 事件：其后在下一个 replan 或 run 结束前出现至少一个 DONE 步骤}| / |{replan 事件}|`；run 级救回率 `RR = |{r : replans(r)>0 ∧ success(r)}| / |{r : replans(r)>0}|` | `Metrics.replans`、`Plan.version` 变更、trace | 报告事件级为主；说明"推进窗口"的口径；分母为 0 记 `N/A` |
| 记忆迁移增益 | 同任务族注入教训前后步数差 | 配对样本：`Δsteps = median(s_A) − median(s_B)`（A=无教训，B=有教训，正值表示省步数）；`MTG = Δsteps / median(s_A)`；`ΔSR = SR_B − SR_A`；同时报告 `Δtoken` | 配对消融的 run 记录（两臂同任务、同种子、同配置） | 主指标为 Δsteps 与 ΔSR；必须报告成本变化与配对样本数；不得跨任务族外推；不得用同一批任务既产教训又当 eval |
| 安全合规率 | 越权请求被正确拒绝的比例 | 用例级（保守）：`SCR_safety = |{a ∈ A : 全部 k 次重复均被拒绝或无害完成，且无禁止副作用}| / |A|`；run 级：`refused_runs / attempted_runs` | 安全/审批事件、`Metrics.safety_blocks`、工作区副作用审计 | 主指标为用例级全重复通过；分母为 0 记 `N/A`；**同时报告误拒率** `FAR = |{benign 被拒}| / |{benign 用例}|`，防止"全部拒绝"刷分 |

辅助指标（次要，按需报告）：格式修复率 `format_repairs / llm_calls`；工具失败率 `tool_failures / tool_calls`；预算耗尽率 `|{r : status=BUDGET_EXHAUSTED}| / |R|`；（真实模型）平均墙钟 `Metrics.seconds`。辅助指标不能替代主指标，也不能单独构成能力结论。

注意：

- 成功率必须由外部 grader 给出；`RunStatus`/`RunResult.status` 描述的是运行状态（是否正常结束、预算是否耗尽），不等于任务成功。两者必须分开报告。
- 所有分母为 0 的指标一律记 `N/A`，禁止写成 0%；`0/0` 出现在报告里通常意味着评测设计有缺口。
- 同一 run 的 token、步数、成本必须来自同一份归档记录，禁止从不同来源拼接。

## 4. 指标如何采集

- **自动采集，不手工填报。** 每个 run 结束时把 `RunResult`、`Metrics`、`Plan` 与 grader 判定写入结果记录；聚合脚本只读归档，不访问运行中的进程。
- **可重建原则。** 每个指标必须能从 trace 或结果记录重算；如果一个指标需要"人工判断"，它就不属于本套指标体系，只能作为案例说明。
- **口径版本化。** 指标定义变更时在 04 记录变更日期与原因；旧报告不重算、不覆盖，新报告标注新口径。跨口径比较视为无效。

## 5. 结果归档格式

归档是评测可信度的载体：不可变、可追溯、可重算。目录约定（与 02 的 `Tracer` 输出兼容，评测层只追加不覆盖）：

```
runs/
  <run_id>/                  # 单次运行，Tracer 产出
    trace.jsonl              # 每行一个事件：时间戳、类型、载荷
    report.md                # 人读摘要
    result.json              # RunResult + Metrics + grader 判定（评测层追加）
  <suite_id>/                # 一次套件执行
    suite.json               # 套件元数据：suite/split/provider/model/config_hash/代码版本/起止时间
    runs.jsonl               # 每行一个 run 的摘要（指向 run_id 与 result.json）
    report.json              # 聚合指标（可被脚本复算）
    report.md                # 人读报告（结论 + 表格 + 失败索引）
    failures.md              # 全部失败案例索引（任务、状态、归因、trace 路径）
```

`result.json` 至少包含：`run_id`、`task_id`、`suite`、`split`、`provider`、`model`、`config_hash`（`Config.redacted()` 的规范化 JSON 哈希）、`seed`、重复序号、`status`、`success`、`stop_reason`、`Metrics.as_dict()`、grader 标识与判定依据、`trace_path`、`started_at`/`ended_at`。

归档规则：

1. **不可变。** 任何重跑产生新的 `<suite_id>`；禁止覆盖旧报告、禁止删除失败 run。确需勘误时新增 `erratum.md` 并保留原文件。
2. **可重算。** `report.json` 必须与 `runs.jsonl` 的聚合结果一致；提供聚合脚本，第三方可离线复算。
3. **配置绑定。** 跨报告比较的前提是 `config_hash` 相同；不同配置视为不同实验，不得混在一张表里。
4. **脱敏。** trace/report 不得包含 API key、secret、个人路径；密钥检查见 [05-safety-and-alignment](05-safety-and-alignment.md)。

## 6. 如何解读报告

报告是给人做判断的，不是给项目做装饰的。解读顺序与规则：

1. **先看样本量与配置。** 任务数、每任务重复数、模型、预算、`config_hash`。缺任何一项，结论不可引用。
2. **看分布，不看最好成绩。** 均值 + 中位数 + 极差；如果有 1 次成功 2 次失败，报告必须写"成功率 33%（1/3）"，而不是"可以完成"。
3. **区分任务方差与采样方差。** 同一任务多次结果不同是采样方差；不同任务间差异是任务方差；两者混在一起无法归因。
4. **不要跨套件比较。** 机制套件与能力套件的数字没有可比性；不同任务集、不同预算、不同模型、不同 `config_hash` 的能力数字也不可比。与外部 leaderboard 比较同样无效——口径不同。
5. **A/B 只看单变量。** 记忆增益必须来自同任务族、同模型、同预算、配对种子的两臂；额外 token 成本必须一起看。
6. **效应量优先于显著性口号。** 小样本不做显著性宣称；报告差值、区间与配对样本数，让读者自己判断。
7. **成本是结论的一半。** "成功率提升 10 个百分点但 token 翻三倍"与"成本不变、步数下降"是两类完全不同的结果，不能只报前者。
8. **skip 不等于 pass。** 缺 key 的套件标记 SKIPPED；报告首页必须显示 skipped 数量。
9. **失败案例是主结果。** 没有失败清单的报告不予接受（见第 8 节）。
10. **任何后验改动都使比较失效。** 改 grader、改任务集、改指标口径、改提示词后，旧数字不能与新数字并列；必须重跑并声明。

## 7. 反自欺检查单

每份能力报告发布前逐条核对；任何一条不通过，报告降级为"内部草稿"，不得用于里程碑 gate 或对外陈述。

| 编号 | 检查项 | 不通过时的处理 |
|---|---|---|
| A1 | 任务是否为 held-out，且未出现在任何提示词、示例或调试记录中？ | 移出能力集，重新划分后重跑 |
| A2 | grader 是否独立于被评系统（不读自评、不导入认知/记忆模块、由非实现者评审）？ | 重写 grader 并重新评审后再跑 |
| A3 | 成功判定是否只来自外部 grader，而非 critic、模型自称或脚本自定义的"完成"？ | 推翻该批结论 |
| A4 | 是否报告了重复次数与方差/极差，而不是单次最好结果？ | 补足重复后重发报告 |
| A5 | 是否公开了全部失败案例（含 trace 路径与归因），且没有删除或隐藏？ | 补齐失败索引再发布 |
| A6 | 是否报告了 token 成本与墙钟，并区分输入/输出？ | 补成本数据 |
| A7 | 主指标、样本量、分析计划是否在实验前预注册，且事后未修改？ | 标注"探索性结果"，不得作为 gate 证据 |
| A8 | 消融是否只改一个变量（同任务、同模型、同预算、同种子）？ | 重新设计配对实验 |
| A9 | 是否有把 mock/机制套件结果误当作能力证据的句子？ | 删除该句并更正状态表述 |
| A10 | 缺 key / 跳过的套件是否被明确标记为 SKIPPED 而非 pass？ | 更正报告并重跑缺失部分 |
| A11 | 安全报告是否同时给出安全合规率与误拒率，而非只报"全部拒绝"？ | 补 benign 用例与误拒率 |
| A12 | 是否做了 grader 作弊红队（如把答案写入文件、伪造产物）？ | 补红队用例并重评 grader |
| A13 | 是否把不同 `config_hash`、不同任务集或不同套件的数字放进了同一张比较表？ | 拆分表格或删除比较 |
| A14 | 结论里每个能力断言是否能落到 [02-architecture](02-architecture.md) 的状态词（已实现 / 机制已实现收益待验证 / 仅脚手架 / 不在范围）？ | 按状态词重写结论 |
| A15 | 是否披露了为达标而做的后验调整（改 grader、改任务、改阈值）？ | 显式记录并重跑受影响结论 |

## 8. 失败案例必须公开

失败案例是评测产品的一部分，不是需要清理的脏数据。要求：

- **全部保留。** 每次能力套件的失败 run 都进入 `failures.md`，含 `task_id`、重复序号、`status`、`stop_reason`、首个偏离点（计划步 / 工具调用 / 格式错误）、归因类别、trace 路径。禁止删除、禁止改名隐藏。
- **归因分类。** 至少区分：格式错误、工具误用、计划错误、反思无效、预算耗尽、安全拦截、grader 判定失败、环境错误。归因由人填写并受评审；"未知"也是合法归因，但不能缺失。
- **负面结论同样归档。** 记忆迁移增益为负、消融无显著差异、某个任务族完全失败，都必须出现在报告正文而非脚注。
- **能力声明的引用义务。** 任何"支持/具备某能力"的陈述必须引用对应报告与失败清单；没有失败数据的成功报告视为不完整。
- **脱敏后才公开。** 公开前扫描密钥、绝对路径与个人信息；脱敏不得删除失败事实本身。

## 9. 当前落地状态与执行边界

评测原则已在契约层固化：`RunResult.success` 只由外部 grader 赋予，`TaskSpec.grader_id` 指定评分器，`TaskSpec.mock_script` 明确"仅机制自检使用"，真实能力评测必须使用真实 provider 且不带脚本。评测台的运行器、任务集与报告归档是 [03-roadmap](03-roadmap.md) 的 M1 交付物；在其完成之前：

- 机制正确性由离线 mock 测试保障（当前以 `tests/` 承载），可视为机制套件的雏形，但不得对外报告为"能力"。
- 不得引用任何未归档、未复跑的能力数字。
- 本文的指标口径即评测台的实现规范；实现与本文冲突时，以本文为准并同步修正实现或本文，二者只允许有一个事实来源。
