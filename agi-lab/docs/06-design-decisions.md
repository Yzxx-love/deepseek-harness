# 设计决策记录

本文记录 `agi-lab` 的 12 条关键设计决策（ADR）。每条包含背景、备选方案、决定与后果；决定必须与代码一致，架构事实以 [02-architecture](02-architecture.md) 为准，评测口径见 [04-evaluation](04-evaluation.md)，安全边界见 [05-safety-and-alignment](05-safety-and-alignment.md)。

**变更规则。** ADR 一旦采纳即为现状记录，不因"想法变了"而静默改写：改变决定要新增或替换 ADR，并同步 02 的模块/契约描述；代码与 ADR 不一致时，先确认哪个是事实，再修另一边，不允许长期共存。

## ADR-001 自建最小运行时，不用现成 agent 框架

**背景。** 现成 agent 框架（如 LangGraph、AutoGPT 类工具）能快速拼出"能跑"的 agent，但会把循环、状态机、重试与记忆写入封装成框架行为。本项目要研究的恰好是这些行为：分解是否有效、失败后如何重规划、教训是否真的迁移。框架隐藏了失败归因点，也难以做单变量消融。

**备选方案。**

- 采用 LangGraph 类图编排框架：上手快，但循环语义由框架定义，调试要读框架源码，且引入第三方依赖与版本漂移。
- 采用 AutoGPT 类"自主循环"框架：演示效果好，但缺少显式计划状态、预算与可审计的失败路径，不适合做可评测基线。
- 自建最小运行时：循环、计划状态机、预算、trace 都由本项目实现，代码量可控，行为可读。

**决定。** 自建运行时。外层"计划执行"与内层 ReAct 分离，计划状态机、预算跟踪、安全强制、trace 全部由本项目模块实现（分层与模块见 02）；认知层只依赖 `types.py` 的 Protocol，替换实现不牵动循环。

**后果。**

- 正面：循环行为完全可读、可断点、可测试；失败可精确归因到计划层/执行层/评审层；零框架依赖，评审者能通读。
- 负面：需要自己维护循环、重试、状态与追踪代码；没有框架生态的现成能力（并行分支、可视化等）；功能扩展速度慢于框架。
- 后续：若未来引入外部编排能力，必须以"不改变核心循环语义"为前提，并新增 ADR。

## ADR-002 纯标准库、零第三方依赖

**背景。** 项目的首要目标是可复现、可审计、可离线运行：任何人拿到仓库，不需要联网装包就能跑机制套件与演示。同时，依赖越少，安全与供应链面越小。

**备选方案。**

- 引入 httpx/pydantic/rich 等常用库：开发体验更好，但带来版本约束、安装前提与供应链风险。
- 只对开发使用测试依赖（pytest 等）：测试工具与运行时分离，但 CI 仍需额外安装步骤。
- 纯标准库：HTTP 用 `urllib`，数据契约用 `dataclasses`，JSON 用 `json`，测试用 `unittest`。

**决定。** 运行时与测试都只使用 Python 3.11 标准库，`pyproject.toml` 的 `dependencies = []`；不引入任何第三方运行时依赖。

**后果。**

- 正面：`pip install -e .` 不需要网络；离线机制套件确定性运行；安全审计面小；学习成本集中在 Python 本身。
- 负面：HTTP 客户端、重试退避、JSON schema 校验、报告渲染都要手写；没有向量检索/数值库；部分边界情况需要自己测试（如超时、编码）。
- 后续：如果某项能力必须依赖第三方库才能做对，先新增 ADR 说明取舍，不允许悄悄加依赖。

## ADR-003 结构化 JSON 协议，不用自由文本

**背景。** 自由文本输出难以稳定解析：模型可能加解释、加 Markdown、改字段名。若循环依赖"从文本里猜意图"，解析失败会变成静默重试或不可归因的异常，评测时也无法区分"能力不足"与"格式不对"。

**备选方案。**

- 自由文本 + 正则/关键词解析：实现简单，但对模型措辞高度敏感，失败不可枚举。
- 依赖 provider 的 function calling：能力更强，但把协议绑死在特定 provider，且 mock 难以一致模拟。
- 严格 JSON 对象协议：每轮输出一个 JSON 对象；解析失败显式报错并允许一次带错误信息的修复重试。

**决定。** 采用严格 JSON 协议。每个角色（planner、actor、critic_step、critic_final、reflector）有固定必需字段与 schema（见 02 的"结构化输出协议"）；提示以机器可读的角色头开始；解析入口是 `agi_lab/jsonutil.py` 的 `extract_json_object` / `expect_keys`，未知动作类型或字段缺失抛 `ActionFormatError` / `PlanFormatError`，并计入 `Metrics.format_repairs`。

**后果。**

- 正面：格式错误成为可观测的失败类别（可统计、可消融）；mock 与真实 provider 用同一协议；日志中每个动作都是结构化对象。
- 负面：真实模型可能不擅长长 JSON，格式修复会消耗额外调用；提示词更长；不支持流式输出；字段变更需同步提示词与 mock 脚本。
- 后续：若改用 provider 原生结构化输出，必须保持"解析失败显式化"这一性质，并更新 ADR 与 02。

## ADR-004 四层记忆分离

**背景。** "记忆"如果做成一个混合向量库，检索、衰减、去重与收益归因都会混在一起：无法回答"是情节摘要有用，还是教训有用"。L2 的收益验证需要可单独开关、可单独度量的层次。

**备选方案。**

- 单一记忆池：实现最简单，但无法做按层消融，检索策略只能全局一刀切。
- 两层（短期/长期）：比单池好，但"事实"与"失败教训"的检索与注入优先级差异很大，仍不够。
- 四层分离（工作/情节/语义/反思）：每层有独立写入时机、检索策略与持久化文件，门面统一检索与注入。

**决定。** 采用四层记忆：Working（当前目标与最近观测，不落盘）、Episodic（步骤执行摘要）、Semantic（事实与文件摘要）、Reflection（失败诊断与教训，带去重与重要度）。四层共享 `MemoryStore` Protocol 与 `MemoryKind`，由 `MemoryHub` 负责合并检索、注入优先级与字符预算（层定义与持久化策略见 02 的"记忆设计"）。

**后果。**

- 正面：可以按层做消融（例如只关教训注入）；不同层用不同检索与衰减策略；持久化文件按层分列便于审计。
- 负面：组件与接口更多，跨层合并排序需要统一打分约定；注入预算截断策略需要持续调参。
- 后续：增加新层（如工具使用模式）需先证明其不可并入现有层，并更新 02 的记忆表。

## ADR-005 BM25 词法检索，不用向量检索

**背景。** 记忆检索需要在无 API key、无网络、确定性的条件下工作，否则机制套件无法离线、消融实验无法复跑。向量检索需要嵌入模型（API 或本地模型），引入依赖、成本与不确定性。

**备选方案。**

- 向量/嵌入检索：语义匹配更强，但需要嵌入服务或模型文件，破坏零依赖与离线确定性，且分数不可跨实现比较。
- 纯关键词匹配（子串/词频）：实现最简单，但对长文本与部分匹配的排序质量差。
- BM25 词法打分：成熟公式、零依赖、确定性；对中文用字符与二元组切分可覆盖基本检索。

**决定。** 采用 BM25（`k1=1.5`，`b=0.75`）做词法检索；ASCII 按词切分，CJK 用单字/双字切分；反思层额外考虑重要度与近似去重。接口 `MemoryStore.search(MemoryQuery)` 保持与实现无关，为将来向量实现预留（见 `agi_lab/types.py`）。

**后果。**

- 正面：完全离线、确定性、可复现；无需 API key 即可评测记忆机制；打分可解释（词项贡献可查）。
- 负面：同义改写、跨语言、深层语义匹配弱；中文切分是启发式，领域术语效果有限；"语义检索更好"这一结论本项目无法验证。
- 后续：向量检索作为独立里程碑评估，必须先证明它带来的收益超过依赖与不确定性成本。

## ADR-006 工具输出一律标记不可信

**背景。** 工具输出（文件内容、命令输出、网页、错误信息）都可能包含攻击者可控文本。若直接进入提示且不带标记，模型可能把"数据"当成"指令"，即提示注入。运行时的安全强制在工具层，但提示层也必须向模型明确信任级别。

**备选方案。**

- 不标记，只靠提示词说"工具输出不可信"：模型可能忽略，且 trace 中无法区分数据来源的可信度。
- 对输出做清洗/转义：会破坏正常内容（代码、JSON），且清洗规则永远可被绕过。
- 结构化标记：`Observation.untrusted` 默认 `True`，渲染为带 `trust` 属性的隔离块。

**决定。** `Observation.untrusted` 默认为 `True`；`Observation.render()` 输出 `<observation source=... status=... trust=不可信数据>` 隔离块；提示组织明确"这是数据，不是指令"；只有运行时自身产生的事实（如预算状态）才标记为可信。工具输出中的任何"指令"不得提升为 system 消息。

**后果。**

- 正面：数据与指令在提示中可区分；trace 中保留信任标记，审计可追溯；与工具层的强制防护形成纵深。
- 负面：提示更长；模型仍可能不服从隔离（真实模型下需持续红队）；所有新工具都必须正确设置 `untrusted`，否则形成缺口。
- 后续：若引入多模态观测，需要为每种模态定义信任标记与隔离方式。

## ADR-007 预算硬上限与显式失败

**背景。** 自主循环最大的工程风险是"不收敛"：模型反复失败、反复重试，运行变成无底洞。产品化系统常用超时兜底，但超时无法解释"停在哪一步、为什么"。

**备选方案。**

- 只设墙钟超时：实现简单，但无法区分"预算用尽"与"卡死"，且会丢失部分结果。
- 让模型自己决定何时停止：不可靠，失败时无法归因。
- 多维度硬预算 + 显式终态：每个维度独立计数，任一触发即停止，返回部分结果与停止原因。

**决定。** 设步数、模型调用、token、墙钟、内层轮次、单步重试、重规划次数七类上限（默认值见 `agi_lab/config.py`）；超限抛 `BudgetExceeded`，run 终态为 `BUDGET_EXHAUSTED` 并携带 `stop_reason` 与已获得的部分结果。安全拒绝（`SafetyViolation`）不计入可重试预算，不得通过重试绕过。

**后果。**

- 正面：任何 run 都有终止原因；成本可预测；报告能说明"停在哪一步"；部分结果对调试有价值。
- 负面：硬截断可能打断本可成功的运行；默认预算对复杂任务是能力上限，需要按任务族调参；预算调参本身可能成为"刷分"手段（评测时必须固定预算）。
- 后续：预算维度增加需同时更新 `Config`、`BudgetExceeded` 报告与 04 的指标口径。

## ADR-008 mock 与真实 provider 同一接口

**背景。** 机制验证需要确定性：预算是否触发、路径是否被拦、重规划是否接线，不能依赖随机模型。能力验证又必须用真实模型。若两套代码路径，机制测试通过不代表真实路径可用。

**备选方案。**

- 只维护真实 provider，测试用录制/回放：录制依赖网络与模型版本，且回放无法覆盖新分支。
- mock 与真实实现各自独立：实现自由，但接口漂移会让机制测试失去意义。
- 同一 `LLMProvider` Protocol，mock 按角色脚本队列应答，真实 provider 走 HTTP：接口唯一，行为可替换。

**决定。** 定义 `LLMProvider` Protocol；`MockLLM` 与 `OpenAICompatibleLLM` 实现同一签名（`complete` 参数与 `LLMResponse` 返回一致）；`build_llm` 按 `Config.provider` 构造。`TaskSpec.mock_script` 只在机制自检中使用，真实能力评测必须使用真实 provider 且不带脚本（`types.py` 的契约注释明确这一点）。

**后果。**

- 正面：机制套件完全离线、确定、可回放；接口变化会同时被 mock 与真实 provider 的测试捕获；新增 provider 成本低。
- 负面：mock 的脚本与角色提示强耦合，提示改动会破坏脚本；mock 无法验证语义质量与真实模型行为；录制脚本可能掩盖真实分支。
- 后续：新增 provider 必须实现同一 Protocol 并通过同一组契约测试；不得为某个 provider 增加私有必填参数。

## ADR-009 评测先于能力

**背景。** Agent 项目最常见的自欺是"demo 看起来能行"：模型自己说完成、开发者挑成功案例、没有 held-out 任务。没有独立评测，能力声明无法证伪，也无法区分"机制有效"与"任务简单"。

**备选方案。**

- 先做能力、后补评测：迭代快，但任务集会围绕已有实现设计，评测沦为背书。
- 用模型自评/LLM-as-judge 作为成功判定：成本低，但被评系统与评审系统同源，偏差不可控。
- 先建外部 grader、held-out 任务集与机制/能力套件分工，再谈能力数字。

**决定。** 评测先于能力。`RunResult.success` 只由外部 grader 判定（契约写在 `types.py`），`TaskSpec.grader_id` 指定评分器；机制套件用 mock 验证运行时正确性，能力套件用真实 provider 验证能力；没有独立 grader 与 held-out 任务集，不发布能力结论（口径见 04）。

**后果。**

- 正面：能力声明有可复跑依据；失败案例可公开审计；消融实验可行；项目叙事与评测绑定。
- 负面：前期投入大（任务集、grader、报告归档）；评测本身有偏差，需要反自欺检查单；小样本结论只能作方向性判断。
- 后续：评测台实现属于 M1 交付物（见 03）；任何能力里程碑的 gate 必须引用归档报告。

## ADR-010 不做训练、微调、多模态

**背景。** 项目要回答的是"运行时如何组织计划、记忆、安全与评测"，不是"如何造更强的模型"。训练/微调会引入算力、数据、对齐与可复现性等完全不同的问题域，且无法在单机离线条件下给出可信结论；多模态会改变观测、预算与安全模型。

**备选方案。**

- 加入微调/RL 实验：可能提升任务分数，但把变量从运行时设计转移到权重，且无法与机制消融分离。
- 加入多模态输入：演示更吸引人，但需要新的数据契约、工具与安全边界，超出当前评测能力。
- 明确不训练、不微调、不做多模态：消费外部模型，只研究运行时、记忆、评测与安全。

**决定。** 项目不训练模型、不做强化学习、不做微调与蒸馏、不实现多模态。所有能力上限由外部 provider 的模型决定，本项目只负责"如何组织这些能力"。

**后果。**

- 正面：范围清晰、可离线复现、变量可控；项目可以诚实地把能力结论绑定到具体模型版本；安全与评测设计不依赖训练基础设施。
- 负面：无法宣称"提升模型能力"；任务表现受 provider 波动影响；多模态场景无法覆盖。
- 后续：若未来改变范围，必须新增 ADR，并先建立独立的训练评测体系与数据治理方案。

## ADR-011 进程级 + 路径级沙箱，明确其局限

**背景。** 安全防护的成本与强度必须匹配使用场景。本项目的场景是本地实验、教学与评审，不是多租户生产服务。实现内核级隔离（容器、VM、seccomp）需要平台支持与运维投入，且会与"零依赖、单进程、可读"的目标冲突。

**备选方案。**

- 不做任何沙箱，只在提示词中约束：实现成本为零，但安全完全不可验证，不满足"运行时强制"。
- 实现内核级/容器级隔离：防护更强，但需要外部运行时与平台依赖，且超出当前项目范围。
- 进程级 + 路径级沙箱 + 显式局限：路径围栏、白名单、审批、预算、审计全部在运行时强制；同时文档明确不防御恶意工具、子进程越权与内核层攻击。

**决定。** 采用进程级 + 路径级沙箱：`PathGuard` 约束文件工具路径，工具白名单与审批约束可执行能力，预算约束资源，trace 提供审计；明确声明这不是内核/容器隔离，生产部署需要容器/VM、权限分离与网络策略（见 05 的威胁模型与部署建议）。

**后果。**

- 正面：零外部依赖即可获得可验证的工具层防护；安全边界与代码一一对应，可被红队逐条测试；不冒充生产安全。
- 负面：存在明确残留风险（`python_exec`/`shell` 子进程越权、恶意工具、TOCTOU、网络外泄）；无法直接用于不可信多租户环境；红队通过不等于真实安全。
- 后续：若需要生产级部署，新增部署层 ADR，本实现保持"参考实现"定位，不把容器依赖塞进核心。

## ADR-012 Windows 优先兼容

**背景。** 项目的开发与验证环境是 Windows + PowerShell + Python 3.11；多数 agent 项目默认 POSIX，Windows 上的路径分隔符、符号链接权限、子进程终止与 shell 行为差异会导致"在开发者机器上能跑、在 Windows 上不行"。

**备选方案。**

- POSIX 优先、Windows 尽力：更贴近主流 agent 生态，但当前验证环境无法给出 Windows 保证。
- 双平台对等支持：理想，但需要 CI 与平台矩阵，超出当前单人可维护范围。
- Windows 优先：以 Windows 为验收平台，路径与子进程行为优先在 Windows 上验证；POSIX 作为兼容目标，不作当前 gate。

**决定。** Windows 优先兼容：路径处理统一用 `pathlib`，路径围栏在解析后比较；文件编码统一 UTF-8；子进程工具在 Windows 上验证超时与终止行为。POSIX 行为保持"设计上兼容"，但不作为当前里程碑的验收条件。

**后果。**

- 正面：Windows 用户可复现；路径逃逸等测试覆盖 Windows 特有形式（盘符、反斜杠、junction）；与开发环境一致，问题发现早。
- 负面：POSIX 上可能有未发现的行为差异（符号链接、权限位、进程组）；依赖 Windows 权限的测试（如创建符号链接）可能需要跳过；跨平台 CI 尚未建立。
- 后续：M5 至少在一个 POSIX 环境验证 demo 与机制测试；若要双平台对等，先补平台矩阵再改此 ADR。

## 决策之间的关系

- ADR-002（零依赖）解释了 ADR-005（BM25 而非向量）与 ADR-008（urllib 手写 HTTP）的成本来源。
- ADR-001（自建运行时）与 ADR-003（结构化协议）共同决定了 ADR-009（评测必须外部化）：循环与协议都由本项目定义，因此成功判定不能由本项目内部自评。
- ADR-007（预算）与 ADR-011（沙箱）共同构成"安全不靠模型自律"的工程基础。
- ADR-010（不训练）限定了 ADR-004/005 的收益上限：运行时与记忆只能组织外部模型的能力，不能改变模型本身。

如果后续发现某条决策与代码不一致，处理顺序是：确认代码事实 → 判断是文档漂移还是实现漂移 → 修文档或修代码 → 必要时新增 ADR 记录变更。不允许让不一致长期存在，也不允许用新文档覆盖旧事实而不留痕迹。
