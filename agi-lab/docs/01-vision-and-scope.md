# 愿景与范围

`agi-lab` 是一个**可运行、可观测、可评测的通用智能体参考实现**。它不是一个 AGI，也不宣称接近 AGI。本文回答四个问题：为什么需要这样一个工程台、我们如何定义"通用智能体"、项目做什么与不做什么、以及如何判断项目本身的成功与失败。架构细节（模块表、核心循环、数据契约、结构化协议、记忆设计、安全模型、AGI 六维度映射）全部以 [02-architecture](02-architecture.md) 为唯一事实来源，本文不重复。

## 1. 为什么需要这样一个工程台

关于 AGI 的讨论长期缺少可直接检验的对象：多数主张以演示、轶事或跑分呈现，读完无法回答"在什么预算下、对什么任务、以多高成功率、失败在哪里"。这个缺口不是靠更大的模型补齐的，而是靠一套可复现的工程装置补齐的。具体有六个常见缺口：

1. **主张不可证伪。** "它能规划""它记住了"这类判断缺少操作定义、指标和基线，任何人都能各说各话。
2. **演示不可复现。** 提示词写死在代码里，模型输出随机，没有 trace、没有预算记录、没有失败日志；换一个人重跑，结果无法比较。
3. **机制与收益混淆。** 实现了记忆模块，就被说成"具备持续学习能力"。机制存在不等于收益存在——这正是本项目对 L2 的谨慎表述（见 02 能力分级）。
4. **安全停留在提示词。** 靠 system prompt 要求"不要删除文件"不是安全，只是建议。安全必须在运行时强制并留下审计记录。
5. **工程细节被框架隐藏。** 现成 agent 框架把循环、重试、状态管理封装成黑箱，使用者能跑起来，但说不清失败发生在计划层、执行层还是评审层，也无法做消融实验。
6. **缺少可阅读、可批评的最小参照。** 教学、评审和红队都需要一个小到可以通读、行为说得清的实现，而不是一个依赖复杂、行为不可追溯的产品。

`agi-lab` 的定位就是补齐第 6 点，并顺带为前 5 点提供一个可执行的答案：一个单进程、零第三方依赖、每次运行都留下完整事件流的实验室装置。

## 2. AGI 没有公认定义

这里必须先陈述一个事实：**到目前为止，不存在学界和产业界公认、可操作、可用于验收的 AGI 定义。** 各家立场使用的判据彼此不可约化。把常见立场摊开看，会更清楚为什么本项目拒绝用"AGI"作为目标：

| 立场 | 核心主张 | 被追问时如何度量 | 作为验收标准的问题 |
|---|---|---|---|
| 能力阈值派 | 在大多数认知任务上达到或超过人类水平 | 任务集平均分或阈值通过率 | 阈值与任务集都可挑选，"大多数"没有公认边界 |
| 经济影响派 | 能完成大部分有经济价值的工作 | 职业任务自动化比例、经济指标 | 宏观、滞后，无法在单次运行中判定 |
| 认知架构派 | 具备学习、迁移、元认知等类人机制 | 机制存在性与行为实验 | 机制存在不等于收益，需要单独证明（L2 的教训） |
| 规模外推派 | 规模继续扩大即会涌现通用能力 | scaling 曲线与涌现基准 | 需要训练能力，超出本工程台范围 |
| 意识/理解派 | 具备主观体验或真正的语义理解 | 目前无操作化手段 | 不可测量，本项目不做任何承诺 |
| 怀疑派 | "AGI"只是营销标签，不可定义 | 拒绝使用该词 | 与本项目"用能力阶梯替代 AGI"的做法部分重合 |

结论有三条。第一，"是不是 AGI"不是一个可以靠更多工程投入回答的问题，本项目的文档不应假装能回答。第二，可测量的部分必须换成操作定义，否则无法写验收条件。第三，"通用"必须被限定在具体任务族和具体预算内，否则任何系统都能被解释成"还没遇到合适的任务"。

## 3. 本项目的操作定义

本项目采用的操作定义是：

> 在受控预算与显式安全约束下，对一个**未见任务族**完成"分解—执行—失败—反思—重规划—跨任务复用"的闭环，且闭环中每一步都能被外部观测、独立评分和事后回放。

这个定义约束了四件事：

- **任务必须预先给定并可评分。** 任务定义在 `TaskSpec` 中（目标、初始文件、grader 标识、预算覆盖项），评分由外部 grader 判定，不采信 agent 自评。任务与指标口径见 [04-evaluation](04-evaluation.md)。
- **闭环而不是流水线。** 允许失败、允许重规划，失败必须进入反思并影响后续步骤；核心循环见 02 的"核心循环"一节。
- **预算显式。** 步数、模型调用、token、墙钟、重规划次数都是硬上限；触发即停止并携带部分结果与停止原因，不允许"转到出答案为止"。
- **可观测。** 每次动作、工具结果、拒绝、重规划都写入 `runs/<run_id>/trace.jsonl`，可回放、可用于消融对比；详见 02 的"可观测与评测"一节。

项目当前在能力阶梯上的位置是 **L1（计划执行者）已实现，L2（记忆学习者）机制已实现、收益待真实模型验证**。级别定义、各级状态与逐级判据以 02 的"能力分级"为唯一来源，本文不重复该表；路线图上如何推进见 [03-roadmap](03-roadmap.md)。

"通用"在本项目里只有一个可检查的含义：**跨任务族泛化，且不依赖为单个任务写死的流水线**。它与"无所不能"无关，也不隐含任何与人类或商业模型的能力比较。

## 4. 四条判据

项目是否够格称为"工程台"，用四条判据衡量。它们不是并列的宣传词，而是互相约束的：缺一条，其余三条就会退化成表演。

| 判据 | 含义 | 可检查的证据 | 退化形态 |
|---|---|---|---|
| 可运行 | 无 API key 也能完整跑通；单进程；零第三方依赖（`pyproject.toml` 中 `dependencies = []`，Python ≥3.11） | `python -m agi_lab demo` 在离线 mock 下运行 4 个机制演示并返回退出码 0；`python -m unittest discover -s tests` 可执行且结果可复跑 | 只能演示截图，不能重跑 |
| 可观测 | 每个动作、工具调用、拒绝、重规划、预算触发点都有事件；trace 可重建执行顺序 | `runs/<run_id>/trace.jsonl` 与 `report.md`；`agi-lab replay <trace>` 渲染事件时间线，`read_events` 可读取全部事件 | 只有最终答案，失败不可归因 |
| 可评测 | 独立 grader 判定成功；机制套件与能力套件分工明确；失败样本保留 | 评测报告含任务数、重复次数、方差与失败清单；口径见 [04-evaluation](04-evaluation.md) | 自评通过，或只报成功案例 |
| 诚实 | 每个能力主张都标注状态（已实现 / 机制已实现收益待验 / 仅脚手架 / 不在范围）；局限写在显眼处 | 文档状态词汇与 02 一致；"我们不声称什么"专章；安全与部署局限见 [05-safety-and-alignment](05-safety-and-alignment.md) | 用"接近 AGI"暗示替代可测量结论 |

这四条的耦合关系值得说清楚，因为它解释了为什么本项目先做评测台而不是先做能力：

- **可运行 + 可观测**才构成实验：能重复触发同一个现象，才能讨论失败原因。
- **可观测 + 可评测**才构成证据：日志本身不是成绩，必须由独立 grader 判定。
- **可评测 + 诚实**才构成可信度：否则评测会被用来挑选有利结果（反自欺检查单见 04）。
- **可运行 + 诚实**才构成工具：一个明确说自己能做什么、不能做什么的最小实现，才有被他人复用和批评的价值。

## 5. 范围内（本项目做什么）

以下能力属于当前实现与当前验收范围。它们与 02 的分层和模块表一一对应，本文只列"做什么"，模块归属、接口签名和循环细节以 02 为准：

- **计划执行与重规划（L1）**：显式分解目标、按依赖执行、失败后由评审与反思驱动重规划；`Plan`/`PlanStep` 状态机与终止条件见 02 的"数据契约"与"核心循环"。
- **四层记忆与教训复用（L2 机制）**：工作/情节/语义/反思四层记忆，跨任务检索并注入提示，持久化到状态目录；层定义、检索与落盘策略见 02 的"记忆设计"。
- **工具与路径沙箱**：计算、文件读写、目录列举、删除、Python 子进程、记忆检索/写入，以及需显式开启的 shell 与 HTTP；路径围栏与注册表见 02 的"安全模型"。
- **预算与显式终止**：步数、模型调用、token、墙钟、内层轮次、重试、重规划全部硬上限；状态 `BUDGET_EXHAUSTED` 携带停止原因与部分结果。
- **结构化输出协议与格式修复**：模型每轮输出单个 JSON 对象，解析失败执行一次带错误信息的修复重试；角色 schema 见 02 的"结构化输出协议"。
- **双 provider**：离线脚本化 `MockLLM` 与真实 OpenAI 兼容 provider 实现同一 `LLMProvider` 接口；mock 只用于机制自检与回放。
- **可观测与回放**：JSONL trace、人读报告、从 trace 渲染事件时间线；离线 demo 覆盖四类机制（工具调用闭环、多步计划与文件读写、失败恢复与重规划、安全拦截与审计，见 `agi_lab/demo.py`）。
- **评测台**：独立 grader、任务集、机制套件与能力套件的分工与指标口径（见 04）；评测台实现属 M1 交付物。
- **CLI 与配置**：`run` / `demo` / `eval` / `tools` / `replay` / `config` 六个子命令；配置来自环境变量与显式参数，加载期校验（`Config`）。评测模块缺失时 `eval` 显式报错（退出码 2），不静默通过。
- **安全与审计**：路径围栏、工具白名单、不可逆操作审批、不可信数据隔离、资源预算、审计记录；逐条落地见 05。

## 6. 非目标（本项目不做什么）

非目标不是"永远不做"，而是"不在当前验收范围内，不据此做任何能力声明"。重新评估的条件写在 03 的里程碑里。

| 非目标 | 原因 | 重新评估时点 |
|---|---|---|
| 训练、微调、强化学习、蒸馏 | 工程台消费模型，不生产模型；训练会把变量从"运行时设计"转移到"权重" | 不在路线图内；若做，需先有独立的训练评测体系 |
| 多模态（图像、音频、视频） | 当前数据契约与工具全是文本；多模态会改变观测、预算与安全模型 | M5 之后，且需新契约 |
| 解决对齐问题 | 对齐需要目标规范、监督信号与人机交互设计；本项目只预留 hook（审批、预算、trace、独立 grader） | 见 [05-safety-and-alignment](05-safety-and-alignment.md) 的"要开始做对齐至少需要什么" |
| 生产级隔离与运维 | 本实现是进程级 + 路径级沙箱，不是内核/容器隔离，无 SLA | 生产部署建议见 05；实现不在本项目范围 |
| 分布式、多智能体编排 | 单进程单 agent 才能把循环、记忆、预算讲清楚；多 agent 会引入新的通信与归因问题 | 不在当前路线图内 |
| 向量检索 / 嵌入检索 | 零依赖与离线可评测优先；BM25 确定性、无 API key 也能跑。接口已为将来的向量实现预留 | 见 06 的 ADR-005；当前里程碑不评估 |
| 与商业模型/框架的跑分竞争 | 评测口径、预算、任务集不同，跨系统直接排名会制造虚假结论（见 04 的"如何解读报告"） | 不在范围内；只发布自身基线与消融 |
| 自我改进、意识、理解 | 不可操作化；文档不做任何承诺 | 不在范围内 |
| 长期运行的守护服务 | 当前运行是一次性 run；常驻服务涉及调度、凭据、持续成本与运维 | 不在当前路线图内 |

## 7. 我们不声称什么

以下每一条都是**主动声明**，不是免责套话。它们用于防止读者把工程实现误读成能力主张：

1. **我们不是 AGI，也不接近 AGI。** 本项目在能力阶梯上位于 L1（已实现）与 L2（机制已实现、收益待验证），L4/L5 不在实现范围，见 02 的"能力分级"。
2. **我们不声称通用能力优于任何模型或框架。** 没有跨系统同口径评测，就没有排名；见 04 的"不要跨套件比较"。
3. **我们不声称记忆的收益已被证明。** 运行时确实写入并复用跨任务记忆，但"复用教训能降低步数或提高成功率"只能由真实模型下的配对消融给出；那正是 03 中 M2 的 gate。
4. **我们不声称安全。** 这是进程级 + 路径级沙箱，不防御恶意工具实现，也不提供内核隔离；生产需要容器/VM 与权限分离，见 05。
5. **我们不声称解决或部分解决对齐。** 只提供审批、预算、trace、独立 grader 等 hook；对齐所需的目标规范与监督信号不在本项目内。
6. **我们不声称真实模型下逐次可复现。** 采样有随机性，能力评测报告的是分布、重复次数与方差；离线机制套件才是确定性的。
7. **我们不声称评测无偏。** 小样本、任务选择、grader 严格度、提示词敏感性都会影响数字；04 给出解读规则与反自欺检查单。
8. **我们不声称生产可用。** 没有 SLA、没有权限分离、没有容器边界、没有密钥托管；仅适合本地实验、教学与评审。
9. **我们不声称 mock 结果代表能力。** `MockLLM` 是脚本化离线 provider，只验证运行时机制是否正确；把 mock 通过当作能力证据是明确禁止的自欺行为（见 04 检查单）。
10. **我们不声称具备自我改进、理解或意识。** 这些概念不在本项目的可测量范围内，文档不对它们做任何承诺。

## 8. 状态词汇约定

五个词在本套文档中含义固定，跨文档写作必须一致；能力分级本身的状态以 [02-architecture](02-architecture.md) 的"能力分级"表为准：

| 词汇 | 定义 | 使用规则 |
|---|---|---|
| 已实现 | 代码路径存在且被测试覆盖，可以运行 | 必须能指出模块与验证方式 |
| 机制已实现，收益待验证 | 运行时确实执行该机制，但"带来更好结果"没有真实模型数据 | 不得简写成"已实现该能力"；必须带"待验证" |
| 仅预留脚手架 | 只有接口、预算位或中断点，没有完整行为 | 不得写成"支持" |
| 不在范围 | 本实现明确不做，且当前里程碑不验收 | 不写"暂不支持"，避免暗示即将支持 |
| 计划中 | 写在 03 的某个里程碑交付物里 | 不得出现在能力陈述中，只能出现在路线图 |

规则：任何"支持 X"的句子都必须能落到上表某一状态；写不出来就删除该句。文档中若出现与 02 冲突的事实，以 02 为准并在 03 记录变更，不得在两处各写一套。

## 11. 项目自身的成败判据

除能力阶梯外，项目作为"工程台"也有自己的成败判据，避免用 AGI 叙事代替工程质量。

成功的信号（可检查）：

- 一个没有 API key 的人在 Windows + Python 3.11 上克隆后 5 分钟内能跑通 `demo`，并读懂 trace。
- 一个持有 API key 的评审者能按 04 的口径复跑能力套件，得到方向一致的结论，并能看到全部失败案例。
